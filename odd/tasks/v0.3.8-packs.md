# v0.3.8 — Packs como atributo del producto (backlog #10, diseño cerrado con el dueño)

*Estado: en curso (2026-10-30). Diseño cerrado en debate con el dueño (Log L1-L4): el pack es
UN ATRIBUTO MÁS del producto (unidades por pack, default 1) y sirve SOLO para normalizar el
precio. Fuera de alcance por decisión del dueño: ofertas temporales / packs ocasionales sin
código (no se modelan), y cualquier campo a nivel de precio.*

## Specs

- S1: «Y si al carga el producto, el pack es un atributo mas, que por default es 1? Y el pack
  sirve para el calculo del precio normalizado.» — producto gana el atributo `pack` (entero ≥ 1,
  default 1) = cuántas unidades del contenido neto trae la presentación. Columna nueva
  `pack` (INTEGER NOT NULL DEFAULT 1) en local (migración esquema v5) y servidor
  (migración 0006: ALTER TABLE producto ADD COLUMN pack integer NOT NULL DEFAULT 1).
- S2: precio normalizado = precio ÷ (pack × contenido_neto) — contenido neto queda POR UNIDAD
  (fideos: contenido 500 g + pack 10 → el pack trae 5 kg). El unitario (pack 1) y el pack se
  normalizan al mismo $/kg si el precio por pack es proporcional.
- S3: identificación sin cambios — el pack de 3 y el de 5 tienen SU PROPIO código de barras
  (confirmado por el dueño con el caso real de las galletitas): «la cantidad del pack es útil
  solo para normalizar el precio, la identificación es sin problemas». Cada presentación = su
  producto; el artículo los agrupa.
- S4: «Las ofertas temporales no vale la pena tomarlas en cuenta, el producto habitual no es
  ese pack ocasional.» — NO se modela nada a nivel de precio (sin campo `unidades` en precio,
  sin migración de precio). El precio siempre es por UNA presentación del producto.
- S5: UI: el formulario muestra el campo pack (default 1, editable); la ficha y las filas de
  búsqueda marcan «Pack ×N» cuando N > 1 para desambiguar presentaciones.
- S6: compatibilidad: filas existentes (local y servidor) quedan con pack = 1; backups viejos
  importan con pack = 1; la semilla no cambia (pack = 1); la sync viaja como columna normal —
  **el SQL 0006 debe aplicarse en Supabase Studio ANTES de instalar v0.3.8 en cualquier
  dispositivo** (si no, el push de productos fallaría por columna desconocida).

  el precio normalizado por unidad de emedida es importante conocer que el precio se está
